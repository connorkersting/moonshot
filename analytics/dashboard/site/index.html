3Where the tokens went

Each agent request reports four separate counts. A long-running agent re-reads its whole context on every turn, and those re-reads come back as cache reads, so they dwarf everything else. API-equivalent token counts, not billed; output counts are floors.

4Run timeline

Activity in 15-minute buckets, local time (America/New_York, EDT). The loop ran overnight, went quiet for most of the day, was extended for 24 hours, paused, and resumed for tool expansion and v22.

5Blind A/B

Before keeping a new version, a judge subagent watched it and the previous best in random order and picked a winner for each of seven sections, or called a tie. Every comparison ran once (no repeats).

6Audio QC

An audio check measured, for each version, how far dialogue sits above the music and effects bed, and the loudness of each section. Audio QC files exist from v4 on. v5 and v6 measure identically, as do v11 and v12 (picture-only changes; the audio files themselves were not re-checked).

7Data quality

The metric here is whether bad data gets caught before someone builds a decision on it. Raw files are checked on the way in, the warehouse is tested on the way through, and the known gaps are listed rather than hidden.

Known caveats

  • 52% of requests (2670 of 5,114) lack a final output-token count. The main agent is almost complete; builders, researchers and the ingest agent are not, so subagent output totals are floors. Against the client's own end-of-session-1 cost record, the table's output tokens are 53% (745k vs 1.4M); input and cache counts match for two of three models.
  • No dollar prices. The data has none for these model ids, so everything is in tokens. Haiku web-fetch summaries and the compaction call appear only in the client's cost record, not the transcripts.
  • Scores are model judgments from a single pass. One editor critique per version and one A/B run per comparison; no repeats or human raters.
  • Keep decisions that disagree with the A/B tally are surfaced, not hidden. v10 and v11 lost 0-2 and were kept after the picks were reviewed.
  • Identical audio QC for v5/v6 and v11/v12. Plausible (picture-only changes) but not checked against the audio files. Section 3 is labelled 'act 2 stats/chart' to v7 and 'act 2 stats/ascent' from v8, so models key on the section number.
  • Technical-QC click detector is noisy (thousands of candidates per version, every version reads FAIL), so it is not charted.

Methods

Grain
Claude requests: one row per provider message id. Agent runs: one per subagent. Versions: one per exported trailer version (v1 to the latest; an in-progress version is left out of the charts). Critic scores: one per version x critic x category. Loop phases: one per ledger segment or gap between segments. Blind A/B: one per judge pick for one section of one comparison. Audio: one per version x loudness section, and per version x dialogue line. Timeline: one per 15-minute bucket.
Deduplication rule
Responses are logged as several JSONL lines; rows are deduplicated on the provider message id and cross-checked against the request id (summing lines would have inflated cache reads 2.2x). Output tokens are taken only from a response's closing usage line; where it is missing the value is NULL (unknown), never zero, and the streamed placeholder is kept separately as a lower bound.
Active-time rule
Take every request start time from the main agent and all subagents together, sort them, and merge neighbours no more than 5 minutes apart into one interval. Active time is the summed interval length. Parallel subagents count once and an isolated request adds zero. Wall-clock is first to last event of a session part.
Tokens
Input (uncached), cache creation, cache read and output are kept as separate counts and never merged into each other. "Total known" adds the four. Counts are API-equivalent, not billed, and carry no dollar prices.
Times
Local time is America/New_York (EDT). Timeline buckets are 15 minutes.
Stack
Raw CSVs, then dbt (DuckDB adapter) staging, intermediate, core and mart models, then this script (dashboard/build_dashboard.py), which queries the warehouse read-only and writes this page and one local plotly.min.js. No network access is needed to view it.
